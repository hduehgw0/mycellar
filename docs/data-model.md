## 概要

### スキーマは前提ではなく判断

現在のモデルスキーマ(`schema.prisma`)は、その時点の要件に対する判断にすぎない。実装前や実装中に要件と構造が噛み合わないと感じたら、**構造に合わせて要件を削らず、構造の側を疑い、開発者に提示する**。

### 1 行は、現実の何に対応するか

| テーブル     | 1 行                                                  |
| ------------ | ----------------------------------------------------- |
| `Whisky`     | 父が「これは別の酒だ」と思う 1 種類（製品）           |
| `UserBottle` | 手元にある現物 1 本。同じ製品を 3 本持っていれば 3 行 |

**同じ製品が増える → `UserBottle` を足す。／ 違う製品 → `Whisky` を足す。** 本数は列に持たず、`UserBottle` の行数で表す（→ `docs/adr.md` ADR-0015）。

製品は**いつも 1 本以上のボトルを持つ**。登録は製品とボトルを 1 つのトランザクションで作り、編集の本数の下限は 1、全部手放すときは製品ごと消す。DB はこれを保証しないので、ボトルだけを消す機能を足すときは、0 本の製品をどう扱うか（画面に出すか、集計に数えるか）を先に決める。

`Whisky` はユーザーごとに持ち、共有マスタにはしない。`UserBottle` は `(whiskyId, userId)` の組で `Whisky` を参照するので、他人の製品を指す行は DB が拒否する。製品を消すとボトルも消え、ユーザーを消すと両方が消える。

### 「同じ製品」の定義

**製品名**だけで決める。製品名はラベルどおりのフル製品名（例「ザ・マッカラン 12年 シェリーオークカスク」）で、年数・樽・限定版の表現も名前に入る。国・地域・年数・樽・限定版・メモは判定に入れない（→ ADR-0016）。

| 入れない項目     | 理由                                                                                     |
| ---------------- | ---------------------------------------------------------------------------------------- |
| 国・地域         | 製品名が決まれば一意に決まる。判定に入れても区別が増えず、入力漏れで別の製品に割れるだけ |
| 年数・樽・限定版 | 違う物なら製品名が違う。並べ替えや集計のために、機械で扱える値として別に持つだけ         |
| メモ             | 製品についての記録で、製品を区別する材料ではない                                         |

### 重複をどう防ぐか

同じ製品名を 2 回登録できないようにしたい。ただし `name` に一意制約を張っても、大文字小文字・全角半角・空白の揺れで別の値になる。

そこで製品名を正規化した `nameKey` を別の列に持ち、**`userId` との複合で一意制約を張る**。正規化は `NFKC → 小文字化 → 空白・不可視文字の除去 → NFC` の順。`name` は入力どおりに保存し、比較にだけ `nameKey` を使う。`userId` を外すと、誰かが登録済みの製品を他の人が登録できなくなる。

**`nameKey` は列に保存されるので、正規化の規則を変えると既存の行と比べられなくなる**。変えるときは全行の `nameKey` の作り直しと、新たに重なった行の整理が要る。

### 値の妥当性は zod が守る

国・地域・樽の値域（固定リスト）、年数の範囲、「地域は国がスコットランドのときだけ」といった条件は zod だけが知っている。DB が保証するのは構造（NOT NULL・一意・外部キー）だけで、CHECK 制約は置かない（→ ADR-0017・ADR-0018）。

- 固定リストへの値の追加にマイグレーションは要らない
- アプリを通らない書き込み（Prisma Studio・直接 SQL）では、不正な値が入りうる
- 固定リストから値を消したり名前を変えたりすると、既存の行に古い値が残る

### Prisma 6 → 7 で変わったこと

**接続 URL が `schema.prisma` から出た。** datasource に書くのは `provider = "postgresql"` だけ。`directUrl` は廃止され、URL の指定は 2 か所に分かれる。

| 用途                | 指定する場所             | 使う URL                          |
| ------------------- | ------------------------ | --------------------------------- |
| CLI（`migrate` 等） | `prisma.config.ts`       | direct（`DATABASE_URL_UNPOOLED`） |
| アプリ実行時        | クライアント初期化コード | pooled（`DATABASE_URL`）          |

**クライアントの生成先が変わった。** generator は `prisma-client`（旧 `prisma-client-js`）になり、出力先は `node_modules` ではなく `src/generated/prisma`。git 管理外なので **clone 直後は `pnpm prisma generate` が要る**。

### 環境ごとの DB とマイグレーション

環境ごとに別の DB を見る（→ `docs/adr.md` ADR-0014）。

| 環境              | DB                                                    |
| ----------------- | ----------------------------------------------------- |
| ローカル・Preview | dev ブランチ                                          |
| 本番              | 本番ブランチ                                          |
| テスト            | テスト用 DB（手元も CI も Docker Compose → ADR-0020） |

**開発**：`pnpm prisma migrate dev`。`.env` の値が dev ブランチを指すので、本番には届かない。

**Preview**：ビルドのたびに dev ブランチへ適用される。マージせず閉じた PR の分が残ったら `neon branches reset dev --parent` で本番ブランチの状態に戻す（dev の開発用データも消える）。

**本番**：`main` にマージすると、本番ビルドの先頭で `prisma migrate deploy` が走る（`package.json` の `vercel-build`）。失敗するとビルドごと落ちるので、スキーマが古いまま新しいコードが公開されることはない。
