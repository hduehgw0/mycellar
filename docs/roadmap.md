## フェーズ 4 の進め方

設計はまとめて決め、実装は機能ごとに縦に進める。DB・画面・機能を種類ごとにまとめて作ると、使い方が決まる前の列を足したり、同じ画面を何度も作り直したりするため。

```
① 土台を作り直す → ② 方向を決める → ③ アプリの骨組みを変える → ④ 機能を 1 つずつ縦に足す → ⑤ 仕上げ
```

### ① 土台を作り直す

- **目的**：今の機能のまま、コードの書き方と置き場所を整える。③ と ④ の新しいコードを、最初から新しい作りで書けるようにする
- **主な作業**
  - preview でもログインできるようにする（#157）
  - 開発用の DB を Docker で立てる
  - ADR：書き込みを Server Actions にし、読み書きをデータアクセス層に集め、機能ごとのフォルダに置く（ADR-0002・ADR-0011 を置き換え）
  - ファイルの置き場所を移す（#134）→ Server Actions へ移す
  - データアクセス層に移した読み取り（一覧・傾向）にも、テスト用 DB のテストを足す
  - 年数の「NAS と確認済み」と「未確認」を区別する（#121）
- **順番**
  - ② より先にする：作りを変える前に ③ と ④ を進めると、新しいコードを今の書き方（Route Handler）で書き、あとで移し直すことになる。書き方は、② で決めるテーブルや画面に左右されない
  - #157 を最初にする：以降の作業を、マージする前に preview のスマホで確かめられるようにするため
  - #134 は Server Actions へ移す前にする：「移す」と「作り方を変える」を同じ PR に混ぜないため
  - #121 は ② の前に終える：③ 以降で「NAS」と表示し始める前に要る。無いと、年数がわからないだけの製品まで NAS と出る

### ② 方向を決める（コードは書かない）

- **目的**：③ と ④ で作るものを決める。大きく縛り合うことだけを決め、細かいことは ④ で決める
- **主な作業**
  - 欲しい情報を決める（要件の 5 章）
  - ウイスキーのデータセットを調べる（マスタ・候補検索・入力補完ができるか）
  - データモデルを決める（足すテーブルと、Whisky・UserBottle に足す列）
  - モックを作り直す。画面の一覧と遷移もここで決め、短い一覧を残す
  - ③ と ④ の Issue を起票する
- **順番**
  - 欲しい情報 → データセット：何を探すかが決まらないと、調べる範囲が定まらない
  - データセット → データモデル：使えるマスタがあるかで、テーブルの形が変わる
  - データモデル → モック：モックを作るうちに食い違いに気づいたら、データモデルに戻って直す

### ③ アプリの骨組みを変える

- **目的**：② のモックに沿って、全画面にかかる変更を入れる。Issue と PR は分ける
- **主な作業**：デザインの値（色・文字）、ログイン後の着地・ヘッダーとタブ・右上のアイコン
- **順番**：④ より先にする。全画面にかかる変更を先に済ませ、④ の機能を新しい枠の上に足すため。④ と混ぜると、同じ画面を何度も作り直す

### ④ 機能を 1 つずつ縦に足す

- **目的**：1 つの Issue に、マイグレーション・読み書き・画面をまとめて、機能を足す
- **主な作業**
  - 製品 → ボトルの階層・テイスティングノート・マスタと候補検索・写真（実装先を ADR で決めてから着手）など
  - 一覧の検索・絞り込み・並べ替え・ページネーション・PWA 化（`app/manifest.ts` ＋アイコン）
  - 見た目の小さな Issue は、新しい画面で前提を確かめ直す
- **順番**：② で決めた依存に従う（例：マスタ → 候補検索）

### ⑤ 仕上げ

- **目的**：提出できる形にする
- **主な作業**
  - レスポンシブデザイン（`lg` でサイドバー＋グリッド 3〜4 列）
  - キーボード操作と読み上げのアクセシビリティの点検
  - **E2E（Playwright・主要フロー 1 本）＋テスト拡充**
  - **アプリの Docker 化**（`docker compose up` でアプリも立ち上がる。本番は Vercel のまま変えない）
  - README 整理（スクショ・デモ GIF）・アーキ図
  - 予備日
- **順番**：レスポンシブとアクセシビリティの点検は、画面が固まってからのほうが 1 回で済むので、最後にする
